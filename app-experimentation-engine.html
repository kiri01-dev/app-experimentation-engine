App Experimentation Engine

xVector Labs, August 2026 Companion to: synthetic-data-vision.md

The engine

What this document is

xVector copies a customer's production system into a sandbox branch, runs their real app inside it, changes one thing or nothing, and scores the result against an answer key the app cannot see. That is a controlled experiment, and correctness testing is only one of the questions it can answer.

This document defines the engine and every experiment it can run. This tab names the twenty components and nine crossings every experiment draws on, what every experiment inherits, and what can be read off any run — the vocabulary, not yet a picture of any one type. The next tab derives the eight types. Each type then has a tab of its own, ending in that type's own architecture. The closing tab shows what the eight add up to.

Every experiment here runs inside the sandbox branch. If a piece of work does not need the branch, it is not described here.

The types are derived, not listed. Each is a coordinate: which dataset the app runs against, and which lever moves on top of it. That is what lets the set be shown complete rather than merely long.

One naming decision. This is experimentation, not simulation. A simulation predicts, which makes it a model under SR 11-7 and OSFI E-23 and pulls the whole capability into model-risk review. An experiment runs the real system against modified inputs and reports what happened. The difference is a two-week technical conversation instead of a two-quarter validation.

The right-hand column is the admission test. Each of these eight is impossible against a running system. E1 and E2 differ only in what the app runs against. E3 to E8 differ in which lever moves. The next tab derives that structure.

Three of the eight change the app itself: its structure in E6 Chain & model optimization, how it reasons in E7 Instruction optimization, what it knows in E8 Context optimization. The run mechanics are nearly identical. They stay separate types because the three parts have different owners, different failure modes and different costs.

The vocabulary

Every experiment is built from the same twenty parts and the same nine boundary crossings, named once here and reused verbatim in every tab that follows. This is a parts list, not a picture of any one run. Each type's own tab ends with its own architecture — the subset of these parts and crossings that type actually needs, and no others. Once all eight have been through that exercise, the closing tab shows what they add up to and why nothing beyond this list was ever required.

Components — sealed from the app

Fourteen, in five stages.

Stage Component What it does
Define Experiment spec Defines the run before anything executes: what changes and to what values, how many records at what rate, the timing, the random seed, the expected response for each case, the sample sizes, the pass criteria. Versioned, so two runs compare only within one spec version. Nothing runs that the spec does not describe.
Define Fault & scenario library The curated stock the engine draws on: fault categories with matched decoy templates, and shocks taken from real history. It owns the held-out partition, the categories kept out of every tuning loop and used only to check a result. Library coverage is the ceiling on everything the engine can measure, so the ceiling gets an owner and a coverage record. New failure modes are written back here.
Define Configuration & composition registry Everything about the app that can change, and its version. Every parameter, marked tunable or policy-fixed. Every skill and model tier, with its price. Every instruction version and context version — a wording that changes without a stamp ruins any paired run and any drift trend. The registry bounds what a search may touch, makes two versions diffable, and defines what a decoy is a decoy relative to. Sorting tunable from policy-fixed is the first move in any account, and the answer lives here.
Construct Synthetic data generator Builds what gets written into the branch: faults, and matched decoys that look like faults but are correct under the configuration in force. Magnitudes and timing are calibrated against real branch data so nothing reads as synthetic. It emits a label for every record. For every type except E5 Adversarial search it draws from the library; there it sits inside the loop and takes the scoring service's output as its target.
Construct Change engine Applies exactly one change, under the spec. Six levers: data (a past period rebuilt, records added, or a search target for the generator), configuration (thresholds, tolerances, rules on and off), conditions (handed to the harness), composition (which skills, on which model), instructions (how each skill is told to reason), context (what the skills read). The first three land in the branch, composition and instructions reach into the app, context lands in the knowledge store. Holding everything else fixed is what makes a result attributable.
Construct Environment & load harness Sets the conditions a run executes under, none of them writes to the branch: the as-of clock, volume and mix, late or partial feeds, and lifecycle events like restart, cutover and month-end. The same clock steps a replay through a series of as-of dates.
Execute Run orchestrator Builds the spec's run matrix — eleven cutoffs at five repeats, an ablation set, a series of as-of dates — and executes it, holding the seed fixed across a pair. A single run is the simplest case. Nothing reaches the app zone except through it, so the bill can be counted before it is spent.
Execute Isolation monitor (canary) Checks, before every run, that a known answer-key record is absent from every input the app can see, and logs the check with the configuration version. The run does not start if the check fails. Isolation is built into the architecture, but it still has to be tested, and this is what tests it.
Truth Answer-key store What should have happened for every case, with where that truth came from. Observed: already recorded in the customer's systems, as with a chargeback, an 835 remittance or an incident log. Seeded: the generator wrote it. Baseline-relative: a prior run of the same app is the reference. Provenance travels with the result, because the three do not hold up equally.
Measure Scoring service Compares findings to the answer key. Two numbers, defined once and used everywhere. Recall is the share of real problems the app caught. Precision is the share of its flags that were real problems. They are scored separately because missed faults and false alarms are different failures with different fixes. A case flagged correctly stays a true positive whether or not anyone acted on it, and whether or not it was later fixed. Confusing "was the detection right" with "is it still happening" badly understates a working detector, and it is the most common error here. The service also scores materiality, root cause, and, from the execution trace, which step produced the failure. That last one separates a wrong answer from a right answer lost in routing.
Measure Capacity model Reads the same findings through a queueing model: how much human work each operating point creates, whether it clears inside the deadline, at what headcount. It catches a failure no accuracy number can show, and it opens a second budget. Its limitation: the sandbox cannot watch people, so its inputs are estimates.
Measure Cost & runtime meter Inference spend, wall-clock and throughput, per run and per skill, read off the execution trace. It prices a sweep before the sweep is committed, and E6 Chain & model optimization's result is reported in its units. A branch rarely matches production compute, so its timing readings are directional only.
Compare Run history Every scored run kept with the spec version, configuration version and run cost it ran under, and which fault categories were exercised or held out. Drift trends are drawn from it, stressed runs are scored against baselines retrieved from it, and it is what an audit or model-risk function is shown.
Compare Run comparator Compares run A with run B rather than one run against truth: paired inputs, a shared seed, repeats per configuration, and a variance floor separating a real difference from noise. The app is a chain of LLM-driven skills, so two runs on identical input can differ. E3 through E8 all resolve here. E7 Instruction optimization chases the smallest differences and needs the most repeats.

Components — reachable by the app

Six. Two of them are outputs.

Component What it does
Sandbox branch A one-way copy of real production data and the live configuration, isolated from production. A run can change anything inside it and act on nothing outside. That is what makes intervention safe.
Knowledge & context store What the skills reason with rather than about: entity types and properties, relationships, ontology scope, and the retrieval between them and a skill's input. Copied into the branch alongside the data and pinned for the length of a run, because in production it is edited continuously and unpinned context makes any paired comparison meaningless. E8 Context optimization moves it. Every other type holds it still.
App under test The customer's real app, running as a chain of skills. Unmodified, except where the lever is the app itself: composition in E6 Chain & model optimization, instructions in E7 Instruction optimization. It cannot tell which records were changed. If it could, the run would measure whether it can spot a test, not how it handles a real failure.
Integration stubs & egress guard Every outbound call — notification, payment trigger, claim submission, webhook — caught at the boundary, recorded, never sent. The read-only-to-the-world guarantee lives here rather than in a policy, so it is verified against each customer's real integrations at setup and after any change to them. Recording the attempts also lets a run tell a correct finding from one that never reached anyone.
Findings What the app flagged, what it missed, what it wrongly flagged, the severity it assigned, and where it routed each one.
Execution trace Per skill: what it received, what it produced, how long it took, which model it ran on, at what token cost. This makes a miss attributable to a step rather than to the endpoint, and the cost meter reads it. It crosses out alongside the findings and is a separate artifact. Fold it into "findings" and chain attribution gets claimed in a deck and never built.

What crosses the boundary

Nine things, and nothing else may. The count is not the argument; the closed list is.

Five enter the app zone

  1. The change engine writes the changed records into the branch, or rebuilds the past period there. Once written they are indistinguishable from real records.
  2. The change engine rebuilds the app: its composition in E6 Chain & model optimization, its instructions in E7 Instruction optimization. This is the crossing that reaches past the branch into the app, so both types need their own isolation argument.
  3. The change engine writes the context: entity properties, relationships, and the scope a skill is given. Only E8 Context optimization moves it. Every other type depends on it staying pinned, because an unpinned knowledge layer is a lever nobody recorded.
  4. The harness sets the conditions: the as-of clock, the shape and mix of what arrives, feed health, lifecycle events.
  5. The orchestrator starts each run with its seed, once the canary check has passed.

Three leave it

  1. The generator reads real branch data to calibrate magnitudes and timing. The seed list and the labels never come back out.
  2. Observed outcomes are lifted into the answer-key store, then cut from the app-visible copy along with everything recorded after the as-of date. Observed truth sits inside the customer's own data, so an observed answer key can only be built by reading it out of the branch. The cut stops hindsight leaking back. Without this crossing there is no E1 Historical replay.
  3. The findings and the execution trace cross out to be scored. Nothing from the answer key crosses back in.

One standing check

  1. The isolation monitor confirms, before every run, that the canary is absent from every input the app can see.

One loop looks like a tenth crossing and is not. In E5 Adversarial search the scoring service feeds the generator its next candidate, and the generator writes through crossing 1 like any other run. The loop stays inside the sealed zone and nothing extra reaches the app. That is why it is allowed, and why the canary check carries more weight there than anywhere else.

What you measure

The lever decides the experiment. What you read off it is a separate choice, and all five readings are available on any of the eight types.

Correctness — recall and precision scored separately, materiality accuracy, root-cause accuracy, and attribution to the failing step. This is what the scoring service produces by default. The step attribution comes from the execution trace, not from the findings.

Time-to-signal — how long after a problem started the app fired on it. It belongs to E1 Historical replay and it costs: instead of rewinding once, you rewind to each of a series of as-of dates and run at every one, so the bill multiplies by the number of steps. What it buys is "it would have caught this eleven weeks earlier" in place of "it would have caught this". That is the only measurement that prices the cost of not knowing.

One cell stepped forward month by month. At each as-of date the app sees only what had happened by then, so the gap between onset and detection is measured rather than asserted.

Capacity — the same findings read through a queueing model: how much human work each operating point creates, whether it clears inside the deadline that matters, at what headcount. An app that is accurate but clears after the cut-off has failed completely, and no correctness metric shows that. It also opens a second budget in operations rather than risk or technology, and the labelled cases double as a training set for the reviewers. Its one limitation: the sandbox cannot watch people, so the human layer is a model whose inputs are estimates. State that alongside the number.

Run cost — inference spend and wall-clock, per run and per skill, from the cost meter. It is an ordinary reading on most types and the result on E6 Chain & model optimization, where the finding is a composition that costs less and scores the same. It is also what binds first on E3 Policy optimization, where a sweep is many runs and the variance floor multiplies each configuration by its repeat count. Measure one full-slice run before committing to either.

Segment behaviour — any reading above, sliced by what matters: product, channel, geography, customer tenure, and where it is a live question, protected characteristics. The scoring service already holds every case with its outcome, so this costs a dimension rather than a run. Two reasons to take it. An app that performs well on average and badly on a growing segment is failing where the business is investing, and the average hides it. And in lending, insurance, employment and healthcare, "how does it perform across groups" is a procurement question that arrives whether or not anyone prepared for it. A sandbox with labelled historical cases is a better place to meet it than production.

A segment difference is a measurement. What it means is a judgement. Report the first and do not let it quietly become the second.

These are readings of one run, not separate experiments. An operating point sold without the capacity reading is half an answer, because the right threshold depends on how many people are available to work what it produces.

Constraints every type inherits

  1. The sandbox is read-only with respect to the outside world. Nothing the app does inside the branch reaches a real system; the egress guard intercepts every outbound integration. That makes intervention safe, and because the guarantee lives in a component rather than a policy it can be tested. It is confirmed against each customer's integrations at setup and after any integration change.

  2. Fault-library coverage is the ceiling on everything. You cannot measure performance on a failure mode nobody conceived. Every type inherits that blind spot, and E3 Policy optimization actively exploits it. The library is a named component so the ceiling has an owner and a coverage record.

  3. Holdout discipline. Anything that searches, tunes or ranks must keep the library's held-out partition outside the loop and use it only to check the result. Without this, optimization produces confident wrong answers.

  4. Answer-key isolation must hold everywhere. The key sits in a sealed zone the app cannot reach, and nine things and only nine cross the boundary. That is architecture rather than discipline, but it still has to be tested, and the isolation monitor tests it. Every run asserts a canary: a known answer-key record that must never appear in any app-visible input, checked every time and logged with the configuration version. Three arrangements carry most of the risk, and none may inherit assurance from another. Crossing 2 rebuilds the app, so E6 Chain & model optimization and E7 Instruction optimization run their searches inside the loop that holds the labels. Crossing 7 lifts observed truth out of the branch, so anything downstream of E1 Historical replay depends on the cut being complete. And E5 Adversarial search closes the loop deliberately, optimising against scored responses — allowed only because the app still never sees a label. E3 Policy optimization's threshold search sits inside the same loop, and any self-serve arrangement puts the customer inside it too.

  5. Provenance travels with every result. Observed, seeded and baseline-relative do not hold up equally, and a deck that blurs them will be taken apart by the one buyer who notices. Say which kind of truth each number came from.

  6. Data fidelity varies by type; performance fidelity is low everywhere. E1 Historical replay runs on a real past period, E2 Fault injection on real branch data with known records added. E4 Stress & resilience runs on partly constructed conditions, and a constructed shock is worth what the domain judgement behind it is worth. E5 Adversarial search is only as realistic as its plausibility envelope. Separately, a branch rarely matches production compute and IO: correctness claims travel, latency and throughput claims are directional only.

  7. Every result is pinned to a version of everything, or it is not a result. Six levers means six things that can move between two runs, and any one moving unrecorded turns a measured difference into a coincidence. Data, configuration and conditions are stamped today. Composition, instructions and context must be too. One unversioned surface is enough to confound the whole set.

  8. Who runs an experiment is a delivery choice, not a ninth type. Any of the eight can be run by xVector as a service or handed to the customer against their own sandbox. Self-serve raises retention, because a customer with their own experiment library has made the engine part of how they operate. It also strains answer-key isolation, because the customer is now inside a loop you previously controlled end to end. Decide per account.

The map

How the types are derived

Every experiment is two choices.

First, what the app runs against inside the branch. This also fixes where the answer key's truth comes from, because truth comes with the data:

  • A past period rebuilt in the branch — truth is observed, because the outcome already happened and the customer's systems recorded it.
  • Real branch data with generated records written onto it — truth is seeded, known by construction because the generator emitted the label as it wrote.

Second, which lever moves on top. One at a time, everything else fixed. Moving nothing gives a single run scored against truth. Moving one lever gives a pair of runs scored against each other.

There are six levers. Listing them is what makes the completeness claim checkable — ask what a run consists of, and change each part in turn:

Lever What it moves Type
Configuration Thresholds, tolerances, which rules are switched on E3
Conditions The shape of what arrives, and the health of the environment it arrives in E4
Composition Which skills are in the chain, and which model each runs on E6
Instructions How each skill is told to reason E7
Context What the skills know — entity properties, relationships, scope E8
The data itself, searched The generator inside a loop, hunting for the input that defeats the app E5

The first four were enough while the engine was described for a data app. An agentic app has two more surfaces, and they are the least governed. A skill is written in plain language and edited by whoever owns the process. The knowledge layer is edited by business users continuously and by design. Leaving them out did not stop them moving. It only left their movement unrecorded, which is worse, because an unrecorded lever confounds every other measurement.

The sixth lever is different in kind. The first five move something around the data. The sixth moves the data itself — not by choosing a different period or seeding a different fault, but by searching for the input that breaks the app. Every other type puts a fixed input in front of a fixed app. E5 Adversarial search closes the loop between them.

Two dataset rows by seven lever positions — six levers plus none — gives fourteen combinations, and every one is occupied: eight types, no empty cells. It closes for two reasons. The lever list is exhaustive, because data, configuration, conditions and the app's three surfaces are everything a run contains. And both sources of truth are reachable inside the branch.

The engine's full reach. A ninth type needs a seventh lever or a third dataset the app can run against. The levers are the parts of a run rather than a list somebody thought of, so the closure can be checked.

The truth-provenance ladder

Buyers do not attack what you changed. They attack how you know the right answer. Provenance is the axis that predicts sales resistance, and it runs in one direction:

Provenance The challenge How it survives
Observed Weak on the measurement itself, with two limits to state before the buyer does. First, observed truth shows what occurred and what the app would have caught. It does not show that anyone would have acted differently, so measured gap to capturable value is an assumption. Second: observed truth is censored by the app's own past behaviour. History recorded an outcome for the branch of each decision the app took. For the branch it did not take there is often nothing. An order declined leaves no chargeback, a claim held leaves no remittance, an alert nobody worked leaves no disposition. The qualifying test is about the decision, not the data: does the outcome exist because the world produced it, or because the app chose to let it happen? Where the world decides either way — a break investigated, a claim adjudicated, an event assessed — the key is complete. Where it does not, the missing side needs seeded truth or a random-accept holdout the business already runs, and any modelled reconstruction is labelled an assumption. On decisions where it works, replay carries everything: a customer who has watched the app catch their real incident will accept seeded scoring for the rest.
Seeded "You wrote the test, so of course it passes." Held-out categories, decoys that measure precision, and a spec the customer reviewed and signed. Survivable, and the only option once you need coverage of failures that have not happened yet.
Baseline-relative "You are comparing it to itself." True, and that is the point. But it means the claim is only ever it stayed as good as it was, never it was good. If the baseline was taken on an unrepresentative window, every difference measured against it is wrong in the same direction, and nothing in the result will say so. A baseline drawn from run history with its own spec and configuration version stamped, taken on a window given the same scrutiny as the shock, and read alongside the absolute correctness score rather than instead of it. This rung exists because pairing creates it: the moment a lever moves, the unmoved run becomes a reference.

The third rung comes from the lever, not from a new dataset — the app is still running against one of the same two things — so the derivation above is untouched and the grid still closes. E5 Adversarial search sits on the first rung when its perturbations are label-preserving edits to confirmed real cases, and on the second when it generates freely. Which one it is depends on the run, and the spec has to say.

E1 — Historical replay

Primary. Establishes correctness and robustness — sequence first.

What it is

The branch is rewound so the app sees the world as it stood on a past date. The customer's actual deployed app runs against it: the real chain of skills, the live configuration, the real integration surface with outbound calls stubbed. The right answer for every case is what really happened, already held in the customer's own systems. Nothing is manufactured and nothing is labelled by hand.

What is under test is the deployed system, not a description of it. The configuration that is running is never quite the one that is documented, and the branch carries the running one. It also carries the integration surface, which lets a run tell a correct finding from a correct finding that never reached anyone who could act on it.

Why this needs the branch. Production only moves forward. To ask what the app would have done in March you have to put March back in front of it, and the only place that can happen without touching a live system is a one-way copy. Rewinding is a write, and the branch is the only thing you may write to. It also means rewinding everything the app reasons with, not just the records it reasons about: the configuration as it stood, and the knowledge the skills were reading at that date.

What bounds it, and it is the first question to ask. The answer key is whatever the customer's systems already recorded, so this type reaches exactly as far as their record-keeping does. Where somebody's job is to write the outcome down, the key is complete: a reconciliation break is investigated and dispositioned, a claim is adjudicated, an adverse-event report gets a reportability decision. Where nothing was recorded — or where the only record covers the branch of the decision the app itself chose — there is nothing to score against at any depth of history. "Where does the outcome get written down, and by whom?" qualifies an account faster than any question about data volume or retention.

E1 Historical replay is also what the strongest evidence is built on. A configuration sweep against a reconstructed past period rests entirely on observed truth, with no manufactured answer key to attack. See E3 Policy optimization, which is also where the limits of that claim are set out.

Where it is really valuable

Use case What it is Why it is really valuable
Regression gate on every change Before shipping a configuration or model change, replay a settled window under the proposed version and compare its score to the retained run of the version in production The highest-frequency use, and the one that pays for a standing branch. Turns "we think this is an improvement" into a measured number on real outcomes, at the moment the decision is being made rather than a quarter after it shipped
Post-incident: would we have caught it? Something went wrong last week. Replay that window against today's deployed app Answers within days, while the incident is live and the budget is open. Replaying over a requested data extract cannot serve this, because requesting and validating one takes longer than the window in which anyone still cares
Silent degradation Replay a settled period against the deployed app and compare the score to the run retained from acceptance An app that quietly got worse produces no evidence that it did. A check that no longer fires generates no alert, no exception, no record. This is the only instrument that raises an alarm at all. It does not say why — it says stop blaming the feeds and start looking
Go-live acceptance Run the assembled app over a year the customer already lived through, before it is allowed to act on anything The alternative is switching it on and waiting months for enough outcomes to accumulate, during which it is either acting unsupervised or being checked by hand. Replaying a settled year gives the same verdict now, against known outcomes, on the sponsor's own history rather than a vendor's claim

Worked example — capital markets, silent degradation

Illustrative. The figures are fabricated; the mechanism is not.

Accepted at go-live On replay today Blind period Config changes since The one that mattered
96% of breaks caught 71% caught 11 months 63 FX tolerance, 2bp → 15bp

The setup. A pre-run reconciliation app holds a market-risk batch when book-level positions fail to tie out. Fourteen months ago it was accepted against a replayed quarter, catching 96% of the breaks that later proved material, and it has been live since. Breaks reaching the risk run have been creeping up for two quarters, and the desk has been blaming upstream feed quality.

The app carries roughly 340 configurable parameters — tolerances, book scopes, rule switches — which change constantly and legitimately as products and books change. Sixty-three changes in fourteen months is ordinary, not a red flag. Drift is the baseline condition here, not the anomaly, which is why nobody was watching it.

Two measured runs, fourteen months apart, both retained in run history with the configuration version they ran under. The dotted line is what a monthly cadence would have read over the same period.

The run. The branch is rewound to a fully-matured quarter, one where every break that mattered was later investigated and dispositioned, so the observed answer key is complete. Today's deployed app runs against it once. No lever moves. It catches 71% of the breaks that mattered. The comparison is not to a second run made now but to the acceptance run already in run history. That is what makes this a single run rather than a paired one.

What it settled. One fact: 71%, down from 96%, on the same period against the same recorded outcomes. That is the whole contribution, and it is enough to end two quarters of blaming the feeds. Nothing in production could have produced it, because a break that is no longer flagged generates no alert, no exception and no record.

Locating the cause is separate work. Diffing the configuration stamped on the two retained runs gives 63 changes. Filtering to the ones touching detection thresholds leaves six. Sweeping those six against the same period isolates an FX tolerance widened from 2bp to 15bp eleven months earlier and never restored — and that sweep is an E3 Policy optimization run, not this one.

The division of labour matters, because it is easy to credit replay with work it did not do. E1 Historical replay tells you something broke. E3 Policy optimization tells you which thing.

Risks and obstacles

Risk What it means

An app whose decisions nobody dispositions has no observed truth at any depth, and where the outcome exists only for the branch the app took, the key is complete for what it did and empty for what it did not. E2 — Fault injection

Primary. Establishes correctness and robustness — sequence first.

What it is

Write known faults into the branch, along with matched decoys that look like faults but are correct under the configuration in force. Then score three things: what the app caught, what it missed, and what it flagged that it should not have. The chain is instrumented too, so a miss can be traced to the step that caused it.

This is the type that keeps a number alive past the day it would otherwise die. Every xVector app is already built with an answer key. A generation spec with coverage minimums and matched decoys. Ground-truth fields in a dataset no skill may read. A held-out fraction, and a performance report scoring the app against all of it. Then the app goes live, real data replaces the constructed world, and the ground truth is no longer there. The apparatus is switched off by design, because nothing is left for it to score. The accuracy figure in the validation file was true the day it was measured, and cannot be contradicted afterwards.

E2 Fault injection is that same measurement, continued: on real branch data rather than a constructed world, on a schedule rather than once, and without being rebuilt by hand for every app. It covers failures that have not happened yet and can be described in advance; E5 Adversarial search reaches the ones nobody could describe and writes each one back here, which is how this type's ceiling rises. It is bought defensively, which is its commercial weakness, and defensive purchases are the first thing squeezed in a budget cycle. The go-live cliff is the argument that survives the squeeze, because it names a specific day on which the customer's own evidence stopped being evidence.

Why this needs the branch. Writing a known fault into a live system is not a test, it is an incident. And the place that built the answer key has nowhere to put one. Its ground truth was constructed alongside a synthetic world, not written onto real records, and it is gone by the time the app is doing anything that matters. The branch is what lets a real-looking failure go into real data, watched by the real deployed app, with nothing downstream acting on the result.

E3 — Policy optimization

Primary. Establishes correctness and robustness — sequence first.

What it is

Hold the dataset fixed and change the app's settings — thresholds, tolerances, which rules are on — then re-score each version against the same answer key. Because every case has a known right answer, you can measure what a setting costs and saves instead of arguing about it, and search the range rather than guess at a number.

This is the first of four types that make the system better rather than proving it works, which is a different budget conversation: optimization gets defended in a budget cycle, assurance gets squeezed. E6, E7 and E8 improve the app. This one improves the settings, so the finding needs no engineering change at all. Somebody types a number into a screen and the value arrives the same week.

Why this needs the branch. A sweep means running the same period under a dozen settings. In production you get one setting at a time and pay for each mistake in real money, so the curve can never be drawn. In the branch every point on it is available at once, on the same data, against the same answer key.

Run on seeded data it is credible. Run on a past period rebuilt in the branch — E3 Policy optimization on E1 Historical replay — it is the strongest thing the engine can produce. The result is an operating frontier built on observed truth alone, with no manufactured answer key to attack. It is also the claim that most needs scoping, because it holds only where history recorded an outcome for both sides of the decision.

The qualifying test is about the decision, not the data. Ask whether the outcome exists because the world produced it, or because the app chose to let it happen. A reconciliation break is investigated whether or not it was flagged. A claim is adjudicated whether or not it was held. An adverse event is assessed whether or not intake escalated it. On decisions like those, observed truth covers the whole sweep.

But an order the app declined produces no chargeback, a claim it never submitted produces no remittance, and an alert nobody worked produces no disposition. For those, the range beyond the historical operating point has no recorded outcome. Rewinding the branch replays the past. It does not record what the past never wrote down. Where truth is censored this way, a sweep needs seeded truth or a random-accept holdout the business already runs. Any modelled reconstruction of the missing side is an assumption, and must be labelled one.

One further discipline keeps it honest, and it is one the buyer already respects: tune on period A, validate walk-forward on period B.

The setup. A single cutoff decides decline or accept on every order. Nobody in the business can say whether it is right, because one side of the error is invisible: a declined order that would have been good produces no chargeback, no complaint and no record. The evidence of the mistake is the absence of a sale.

That invisibility is also what makes the experiment hard. Rewinding the branch replays the past; it does not create a verdict the past never recorded. For every order the cutoff declined, history holds nothing, so a looser cutoff cannot be scored on those orders from history alone. What makes this run possible is something the risk team already does for its own model monitoring: a 1.5% random-accept holdout, a small randomly chosen slice of orders let through regardless of score and carried to settlement. Without a holdout of some kind, this run measures the tightening direction only.

Both axes are dollars, and the horizontal one does not exist outside the sandbox. Only the two decision-relevant points are labelled.

The run. The branch is rewound to a fully-matured quarter: 4.1M orders, every chargeback returned. Eleven cutoffs, five repeats each, on a shared seed, with the variance floor set beforehand at ±0.4pp on the share of fraud caught. Orders inside the historical accept region are scored directly against their recorded outcomes. The region the old cutoff declined is scored on the random-accept holdout and reweighted to the full book, so the interval widens: the holdout is 1.5% of the book and carries roughly 1.5% of the evidence.

What it settled. Trading $400K of fraud loss for $4.2M of recovered revenue is not a close call, and it had been invisible for three years. Three disciplines keep it honest. The recovered-revenue figure rests on the holdout rather than the full book, so it is reported as +$4.2M ±1.1M and never as a point. The chosen operating point is validated walk-forward on the following quarter, not the one it was tuned on. And the capacity reading runs alongside: the looser cutoff sends 340 more orders a day to manual review against a team that clears 400 in a shift, so the recommendation is the looser threshold plus two reviewers. The threshold without the headcount would have failed within a week.

E4 — Stress & resilience

Primary. Establishes correctness and robustness — sequence first.

What it is

Change the conditions the app runs under rather than the correctness of the data, and measure whether accuracy and timing hold. Nothing in the data is wrong; the world around it is harder than usual. Conditions means two things. The shape of what arrives: the mix of products, channels, customer types and geographies. And the health of the environment it arrives in: a feed running late or half-empty, a month-end close, a restart, a cutover.

Shape matters more than size, and that is the correction most peak-readiness conversations need. A chain of LLM-driven skills does not get less accurate because there are more records in front of it. It gets less accurate because the records stop looking like the ones it was tuned on. A real peak is worth reproducing because it brings a different mix with it, not because the multiplier is the mechanism. The worked example below is a peak, and the loss in it comes entirely from mix.

The answer key is the baseline run's own output, retrieved from run history and written into the answer-key store as baseline-relative truth. Stress is a paired comparison by nature. The question is not "was it right" but "did it stay as right as it was." Read the absolute correctness score alongside it: that is what tells you whether a run holding its ground was holding a good position or a bad one.

These are two experiments with two buyers, on one lever. Shape — mix, population, segment share — is a decision-quality question owned by whoever owns the risk or analytics number. Environment — feed health, timing, restart, cutover — is a resilience question owned by operations. Running both under one spec is efficient. Selling them as one thing is not.

It also moves the product from does it work to when does it stop working, and buyers find the second question more interesting because they already assume the answer to the first. It recurs on a calendar, and seasonal means budgeted.

Why this needs the branch. Nobody can put a live business through a peak, a shortage or a feed failure on demand. If they could, the cost of finding out that way is the thing they were trying to avoid. The branch is the only place conditions can be imposed rather than waited for.

E5 — Adversarial search

Primary. Establishes correctness and robustness — sequence first.

What it is

Every other type puts a fixed input in front of the app. This one searches for the input. The generator runs inside a loop, reads how the app responded, and produces the next candidate — hunting for the case the app misses, or the smallest change to a real case that flips its decision.

That inversion is the point. E2 Fault injection asks does the app catch the failures we thought of, and its ceiling is the imagination in the library. E5 Adversarial search asks what does it take to get past this app, and the answer is produced by the search rather than supplied to it. It is the only type whose output raises the ceiling every other type inherits, because every successful evasion is a new fault category written back to the library.

This is not only about attackers. Any app that classifies, scores, thresholds or routes has a decision boundary this can map — an approval cutoff, a denial-reason boundary, a materiality threshold — and none of that requires a hostile actor on the other side. The same search, pointed at an ordinary routing threshold with no adversary in sight, answers an equally concrete question: is the cutoff actually where the business thinks it is.

Where it does have a budget line already attached is fraud, AML, claims and content moderation. Somebody there is paid to ask how hard the control is to defeat. Today they answer with a red-team exercise, a workshop and judgement. This answers with a distribution.

Why this needs the branch. You cannot hunt for your own system's blind spots against the live system. A probe that succeeds is an incident. A probe that fails is still a real transaction that acted on the world. A search runs thousands of them. The branch is the only place a system can be attacked without the attack being real.

It is how much a competent fraudster would have to change before the app stopped noticing.

Evasion distance by fraud category. The median is the least interesting number on the chart; the spread is the finding.

The run. Four hundred historically confirmed fraudulent claims, all of which the app caught. The generator perturbs each one inside a plausibility envelope taken from the fault library and the SIU's own case notes: changes a real claimant could plausibly make and a real adjuster would not blink at. A different repair shop, the incident time moved by a few hours, the description reworded, the claim split across two submissions. Every perturbation is label-preserving by construction, so the claim is still fraudulent and the truth is still observed. The search stops at twenty edits or at the first miss.

What it settled. The median is three edits, lower than anyone in the room expected, and not the useful part. The distribution is: two categories survive past twelve edits, and one — staged collisions involving a single repeat claimant — fails at the first, because the app was relying almost entirely on an exact-name match that a middle initial defeats. That is a one-line fix that two years of recall reporting never surfaced. Eleven distinct evasion families went back into the library, where E2 Fault injection now runs them on schedule against every future configuration.

Risks and obstacles

Risk What it means
Unconstrained, it finds curiosities rather than vulnerabilities An optimiser will happily produce an input no human would ever submit, and a defeat by an impossible case is not a finding. The perturbation set has to come from the fault library and from domain case notes rather than from the search's own imagination, and the plausibility envelope belongs in the spec where the customer can review it
This type runs hardest against answer-key isolation Every other type keeps the key away from the app. This one deliberately optimises against scored responses, which is the arrangement the sealed zone exists to prevent. The loop is legitimate only because the app still never sees a label. The canary check and the held-out partition are the entire defence here, and a self-serve arrangement puts the customer inside the loop
There is no natural stopping rule A search with enough budget always finds something eventually, and "we kept going until we found something" is not a result. The edit budget, the plausibility bound and the pass criteria go in the spec before the run. Otherwise the finding is a statement about how long the search ran

The architecture for this experiment

The generator moves inside the loop: the scoring service feeds it the next candidate, which it writes through crossing 1 like any other run. Every component is one the engine already has. What is new is the direction of one arrow, and the loop staying inside the sealed zone is what makes it permissible. The one component this type does not touch is the harness — a search changes what the app sees, not the conditions it runs under.

E6 — Chain & model optimization

Secondary. Optimizes an app that already passes the primary five — sequence second.

What it is

Change the app's structure rather than what the app sees: which skills are in the chain, and which model each one runs on. Re-score against the same dataset and answer key, and read the difference. Because the scoring service already attributes failures to the step that caused them, the engine can say which skill a change affected rather than only that the endpoint moved.

Structure is one of three ways an app can change. The other two have tabs of their own: how each skill is instructed is E7 Instruction optimization, what the skills know is E8 Context optimization. The run mechanics are the same across all three. Structure is the one with an engineering owner and a change-control process behind it.

It reduces the customer's running cost rather than adding to it, which makes it among the easiest to fund. E7 Instruction optimization and E8 Context optimization do the same on their own surfaces, since shorter instructions and leaner context are also paid for on every record. The three add up, because they touch different lines of the same bill.

It is also xVector's own margin lever, though the transfer is weaker than it first looks. A cheaper model shown safe for a skill on one customer's data has not been shown safe on another's, and data-dependence is the whole reason the measurement was needed. What a result travels as is a hypothesis worth testing cheaply everywhere else, which turns an open search into a confirmation. Across a fleet of accounts that is worth a great deal, and it does not require a claim that will fail on its first counter-example.

Why this needs the branch. Swapping a model or removing a skill in production is the change you are trying to decide whether to make. The branch lets the decision be measured before it is taken, and lets a worse composition be discarded without anyone downstream seeing its output.

Worked example — healthcare RCM, inference cost

Dataset Compositions Cheapest safe change The expensive one The hidden finding

The setup. A denial-prevention app runs a five-skill chain on every claim: extract, normalise, check eligibility and authorisation, apply payer rules, compose the finding. At 18,000 claims a month the inference bill decides whether it runs on the full stream or a sample, and a sampled scrubber catches a proportional share of the problem, which is to say most of the value is lost.

One axis, one unit: recall cost in percentage points. The run-cost saving is a direct label rather than a second scale.

The run. The dataset is held fixed — a settled quarter where every claim's outcome is known. Five compositions run, eight repeats each, against a variance floor set first at ±1.2pp on the share of problems caught, because the differences being chased are small and the noise is not.

What it settled. Moving the extraction skill down a tier costs 0.4pp of the problems caught, inside the noise floor, and takes 31% off the run cost. Moving the payer-rules skill down costs 9pp, which is the whole product. Ablating the normalisation skill costs 14pp, far more than anyone expected, because chain attribution shows the payer-rules skill silently depending on normalised inputs it was assumed to handle itself. The finding is a composition that costs 31% less and measurably nothing in accuracy, plus one dependency nobody had documented. The second is arguably worth more, and it surfaced only because failures attribute to the step rather than the endpoint.

E7 — Instruction optimization

Secondary. Optimizes an app that already passes the primary five — sequence second.

What it is

Change how a skill is told to reason — the plain-language instruction itself — holding the data, the configuration, the model and the shape of the chain fixed. Re-score against the same answer key and read the difference. Where E6 Chain & model optimization moves the app's structure, this moves its behaviour inside that structure.

This is the highest-frequency change anyone makes to an agentic app and the least measured thing in it. Skills are written in plain language by people who are not engineers, which is the point of them. A wording gets edited because someone thought it read better, the room agrees, and nothing establishes whether it works better. Over a year an app accumulates dozens of these edits, and its instruction set becomes the product of accumulated taste.

The consequence reaches past this tab. An unversioned instruction is a hole in every other type's attribution. If a wording can change between two runs without leaving a stamp, E1 Historical replay's drift alarm cannot separate the app degraded from someone reworded a skill last Tuesday. Every paired comparison is confounded by any edit made between its two halves. Fixing that is a platform requirement, not an experiment-design one — see the platform assumptions on the engine tab.

Why this needs the branch. You cannot A/B a wording across a live book. Half the traffic would go to the worse instruction, on real decisions with real consequences, and in most operational settings the volume needed to separate two wordings at the noise floor is a large fraction of a quarter's production. In the branch the same records go to every variant, on a shared seed, as many times as the floor requires.

Risk What it means
This type overfits faster than any other The search space is unbounded — there are always more wordings — and the signal is small. That combination manufactures confident nonsense. E8 — Context optimization

Secondary. Optimizes an app that already passes the primary five — sequence second.

What it is

Change what the app knows rather than how it reasons: the entity properties, relationships and ontology scope the knowledge layer supplies to each skill, and how much of it goes in front of the skill on any given record. Hold the data, the configuration, the model, the chain and the instructions fixed, and read the difference.

Context is the third surface of an agentic app, alongside structure (E6 Chain & model optimization) and behaviour (E7 Instruction optimization). It has the least engineering supervision, because enriching a knowledge graph is deliberately a business-user activity. It also costs money on every record, because context is paid for in tokens each time a skill reads it.

The question this settles is one every knowledge-graph investment eventually faces and nobody currently answers. Teams spend quarters enriching entity properties and relationship depth on the reasonable belief that a better-informed agent reasons better. Some of that is true and some is decoration, and until the two are separated the next quarter of enrichment is funded on faith.

Why this needs the branch. The knowledge layer is shared, live, and edited continuously by people whose job is to edit it. You cannot hold it still in production long enough to measure anything, and you cannot roll a harmful edit back without losing every other edit made since. In the branch, context is a version like any other input: pinned for a run, swapped between runs, restored afterwards.

The architecture, combined

What eight independent designs add up to

Each tab above built its own architecture from what that one experiment needed — its own components, its own crossings, argued in that tab's own terms. None of them were handed this picture first. This is what they add up to once all eight are on the table.

Twenty components in two zones, laid out as the stages of a run. Nine things cross the boundary: five in, three out, one standing check. Nothing else may.

No type needed a twenty-first component or a tenth crossing. E3 Policy optimization and E4 Stress & resilience each independently arrived at using all twenty — two held optional in each case, but a different two, for different reasons: E3's search doesn't need to alter the environment, E4's environment-only runs don't need to generate anything. The other six each dropped one or two outright, for reasons specific to that type — E1 Historical replay has nothing to generate, E2 Fault injection runs once so it has nothing to compare, E5 through E8 change nothing about the conditions the app runs under so the harness sits dark. No component exists for only one type: the harness is the only one ever switched off, and even it is active — core in two types, optional in two more — across half the set. That is the finding this tab exists to state — not that a shared architecture was designed and then handed down, but that eight independently-argued designs turned out to need nothing this set does not already contain, and everywhere one of them needed something the set did not have, the set grew rather than the experiment being trimmed to fit.

The wiring is what differs, not the components. Every type uses the branch; what changes tab to tab is which of the nine crossings carry traffic and which components sit dark rather than lit. That is why each per-type diagram is drawn on this same grid, with these same names — not because a template was imposed, but because a shared run mechanism plus eight different levers is what the derivation on The map actually produces.
